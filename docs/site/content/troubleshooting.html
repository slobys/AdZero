网站或 App 打不开

  1. 在概览临时暂停，对比同一个网站或功能。
  2. 若暂停后恢复，打开「访问控制」记录最近拦截，检查相关域名与影响范围。
  3. 先临时放行确认，确有必要再加入永久放行。
  4. 暂停后仍异常，检查代理独立联网、DNS 答案和设备是否绕过路由器。

没有广告并不表示能去掉所有网页空白；同域视频广告也可能无法用 DNS 单独过滤。

数字不变或显示待验证

确认统计组件就绪，并从终端发出新查询。DNS 缓存、加密 DNS、没有新广告请求都可能使计数不变。“待验证”需要电脑执行效果检测命令；不要靠重复手动校验规则来解决。

DNS请求拦截占比不能判断漏拦。如果已知广告域名仍返回真实 IP，先在“访问控制”查询它是否命中当前已应用规则，再用故障设备完成效果检测。未命中应检查规则与放行范围；命中仍返回 IP 则检查接入、IPv6 或设备独立加密 DNS 路径。只看到加密流量或没有计数，不能直接认定绕过；严格模式也不覆盖任意浏览器 DoH。

计数增加但命中域名仍解析出公网地址，需同时检查规则查询结果、当前接入和实际 DNS 应答，不能只改前端数字。

红条、等待锁、关闭并恢复

v0.23.3 起，点击关闭会先保存关闭请求。即使等待操作锁超时，页面也会显示「正在关闭并恢复」，后台继续核对并恢复；刷新页面不会丢失请求。恢复完成前暂停新的开启和规则应用，不需要重复点击或重启路由器。

关闭过程会保留恢复所需的 DNS 辅助服务；即使开关已经关闭但清理尚未完成，后台仍继续恢复。原配置确认载入后才删除自有规则文件、停止后台并显示已关闭。

先展开错误详情，区分上次任务失败与当前保护状态。后台迁移或重载可能暂时持有操作锁；“等待锁超时”不代表已经关闭。等待后点击「重新检测」核对，不手动删锁或恢复记录。

后台同步期间可以点击「排队关闭并恢复」。请求会等待当前操作安全结束，再恢复原设置；不需要反复点击。页面会区分等待操作锁、等待 NaiLink 内核切换、恢复配置及最终核验。

v0.23.2 起，NaiLink 在 dae、sing-box、mihomo 之间切换后，AdZero 根据配置版本、当前内核就绪状态和规则文件确认结果，不再因旧内核名称不同而一直等待。正在切换的内核不会被当成已停止，也不会提前删除规则文件。

NaiLink 的「有修改」也可能是 AdZero 自己尚未完成的 DNS 改动。新版通过配置指纹、选中 DNS／路由、自有文件与进程身份区分自己的未完成操作和外部编辑。必要时，保存的关闭请求可触发有界的 NaiLink 原生服务恢复，连接可能短暂中断；应用和恢复两个阶段各最多一次，普通自动同步不会这样重启代理，也不会重启整台路由器。

如果详情提示 NaiLink 有外部修改，先在 NaiLink 完成或撤销这些编辑，后台再继续核对。节点、群组、全局选项、原生服务配置，以及手动更改过的 DNS、路由或规则文件都保留冲突保护；不会通过删记录或强行显示关闭绕过保护。旧版记录若缺少足够证据，也会保留现场等待处理。

新任务使用随进程释放的内核租约；异常退出后，仅在确认原操作及其子任务均不再持有租约时回收对应记录。未知旧锁、外部文件或仍在运行的写入不会被强行清理。

切换后 Google / ChatGPT 解析异常

若开启并发后出现故障，先看错误是否为国内 TCP 或国外代理 DNS 路径未通过。NaiLink 没有本机 SOCKS 时使用两组单一＋备用、严格关闭；PassWall 国外并发还要求原生 TCP DNS 引擎。不能把 UDP 测速通过当作并发路径正常。推荐起始设置。

先确认唯一活动代理和当前接入，再从故障电脑查询同一域名。比较新查询、旧连接、IPv4/IPv6 与可信加密路径的答案；NOERROR 只表示收到了 DNS 应答。

网络路径恢复后，Windows 可按需清除坏缓存，再重新打开受影响应用：

ipconfig /flushdns

这不能替代路由器修复。如果每次都需清缓存，或 TCP DNS 超时、nftset 持续报错，保留原文分别排查。不要全局清连接跟踪、盲目改全部上游或关闭路径安全检查。

安装时提示「不支持此固件 / 目标架构」

三个固件使用同一份脚本插件，本机包管理器自动选择 IPK 或 APK。兼容性提示通常需要核对原生依赖、软件源与系统包冲突；不再要求用户另选品牌或 ARM64 专用版本。先用菜单预检，保留错误原文并查看兼容说明。

请使用统一安装命令。sh /tmp/adzero-install-auto.sh --detect 只读取本机固件信息；--check 才会下载安装包并检查依赖。不需要改写固件 ID、强装其他 target 或追加其他固件的软件源。

iStoreOS 24.10.8 提示 OPKG/IPK 或版本不匹配

OPKG 系统若提示「本机原生软件包清单不完整」，先重新下载统一安装助手。v0.23.4 修复了把 user、hold 等正常安装标记误判为缺包的问题。旧版菜单或已保存的脚本仍可能使用旧判定，无需为绕过提示改写软件包数据库。

新版仍提示时，会指出未确认的具体包。执行 opkg status base-files luci-base rpcd，只反馈各包的 Package、Version 和 Status 行。仅解包、残留配置或原生查询失败仍会停止；通过清单检查后，还需继续通过本机依赖检查，不能混用其他固件或修订号的库。

让统一安装器按本机实际包管理器选择格式，不要手动把 APK 装到 OPKG 系统。iStoreOS 24.10.8（revision 2026073111）的已知原厂缺失依赖可自动补齐；其他构建先检查自己的源能否满足依赖，不能套用其他修订号的原生库。详见依赖补充范围。

先从菜单选择预检。若计划要求替换已有系统包、依赖仍不满足或旧设置恢复失败，安装会停止；请保留具体错误提交反馈。

iStoreOS 25.12.6 提示「目标需要 APK，当前包管理器或数据库不匹配」

这条报错可能来自旧版安装器使用固定数据库路径或将历史 OPKG 状态文件当成有效包管理器。请重新执行统一安装命令下载新版安装助手；它通过真正的 apk info -e 查询本机软件包，并选择当前正式版。

如新版本仍报错，可只读执行 cat /etc/openwrt_release、apk --print-arch、apk info -e base-files luci-base rpcd tcpdump 并反馈脱敏后的结果。若这些必要组件确实不存在，程序仍会安全拒绝安装。不要删除 OPKG/APK 数据库、强制安装或绕过 SHA-256 校验。

公测版依赖下载失败 / 软件包被拒绝

旧公测包可通过统一入口升级到当前正式版，不再选择品牌或 ARM64 专用渠道。缺失依赖优先由本机原有源提供；iStoreOS 原厂缺失组件按固件版本、修订号和 ABI 精确补齐。

真实包登记冲突、意外系统包替换、DNS 恢复失败或安装不完整仍会中止。请保留错误原文，不使用 --force、删除包数据库、关闭证书／SHA 校验或混用其他固件的 feeds。

升级失败

“没有唯一匹配的 SDK 包”等旧版渠道报错，先改用最新统一入口；共享应用包不要求每个 CPU 单独发布，原生依赖仍须匹配本机。真正的软件源、ABI、配置恢复和系统包冲突应按具体错误处理，保留现有配置。

在线检查提示无法读取版本时，可能是 GitHub 接口连接或访问限制；HTTP 403 本身不足以断言请求配额已用尽。新版可通过官方安装入口后备检查，并分别显示来源状态。稍后重试或用统一 SSH 菜单预检，无需重启代理、反复切换 DNS、提供 Token 或禁用证书校验。安装脚本下载或摘要预检失败也会停止，不再统一描述成固件不兼容。
